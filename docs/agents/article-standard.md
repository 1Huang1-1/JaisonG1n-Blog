# Article Content Standard（Article 内容规范）

本规范适用于 Codex、Claude Code、OpenClaw 和其他 Agent 创作独立博客 Article，是 Article 定位、规划、写作、配图规划、视觉素材检索与复用、生图与图片审查、WordPress 保存与受控发布规则的**唯一完整规则源**。

基础语言、研究和发布规则分别遵循：

- [Writing Style](writing-style.md) — 语言、风格与自检；
- [Research Policy](research-policy.md) — 外部事实核验与来源纪律；
- [Publishing Policy](publishing-policy.md) — 保存、受控发布与已发布内容修改。

本文件**不整份复制**上述基础规范。冲突时：运行时能力以实时 `capabilities` 为准；本文件是 Article 专属规则的权威版本，其他文件中与本文件不一致的 Article 规则一律以本文件为准。

AI 科技日报继续使用 [AI 科技日报固定模板](ai-tech-daily-template.md)，不套用 Article 全流程。Diary 流程见 [Blog Diary Workflow](diary-workflow.md)。

## 1. 定位：Diary 与 Article 的边界

### Diary（日记类）

- 日报和周报；
- 阶段性开发记录；
- 零散实验和进度；
- 强调过程与时效。

### Article（文章类）

- 独立、完整、可长期阅读；
- 有明确问题、主张和结论；
- 有事实、实践或证据支撑；
- 有适用边界和复用价值。

Article 不能只是把 Diary 拉长，也不能只是新闻或资料的重新排列。

## 2. 写作总原则

1. 事实不能为了叙事效果而改写。
2. 个人感受不能为了"像真人"而虚构。
3. 技术结论必须有来源、代码、日志、实验或实际项目材料支持。
4. 主观判断允许鲜明，但必须说明判断依据和适用边界。
5. 图片应帮助解释内容，而不是单纯增加页面装饰。
6. 技术图可以由模型美化，但逻辑结构必须保留可维护真源。
7. 文章在图片无法加载时仍应可以独立阅读。
8. 不把未实现能力写成已经实现。
9. 不把某个平台的 Skill 实现描述为全行业统一标准。
10. 不为了"显得专业"堆叠术语、缩写、来源或复杂图表。

文章应同时具备：严谨性、可读性、真实实践感、明确作者判断、视觉解释能力、长期阅读价值。

## 3. 前置规划

新建长篇 Article 时，写正文前默认生成：

1. 文章目标；
2. 目标读者；
3. 前置知识；
4. 核心问题；
5. 一句话核心主张；
6. 精确到 H2 的结构大纲；
7. 证据与来源计划；
8. 用户已经提供的真实实践材料；
9. 尚缺少或尚未确认的信息；
10. 配图规划；
11. 视觉素材检索计划；
12. 最终输出形式。

用户已经提供明确大纲、确认过规划，或要求重写已有文章时，不重复机械确认，但 Agent 内部仍应执行规划检查。

规划阶段不得：

- 自动保存博客；
- 自动发布；
- 自动生图；
- 虚构缺失的项目经历；
- 把来源计划写成已经读取的来源。

## 4. 推荐文章结构

默认结构：

```text
# 有主张的标题

导语：
- 问题是什么；
- 为什么值得讨论；
- 文章会给出什么结论；
- 必要时说明文章基于什么真实项目或材料。

## 问题与背景
## 核心方案或核心观点
## 总览图、实际证据或运行结果
## 实现过程或深入分析
## 踩坑、失败与修正
## 作者判断
## 适用边界与仍未解决的问题
## 总结
## 资料来源
```

允许按内容调整，不得为了套模板创建空章节。

标题应体现：问题、判断、方法、读者收益。

避免：

- "XX 简介"
- "XX 使用方法"
- "一文读懂"
- "保姆级教程"
- "最强"
- "完美方案"
- 无意义关键词堆积。

## 5. 四类 Article

### 5.1 技术教程 Tutorial

必须包含：

- 操作系统；
- 语言和运行时版本；
- 框架与关键依赖版本；
- 前置条件；
- 可执行步骤；
- 预期结果；
- 常见错误；
- 排查方法。

代码可以是最小可复现示例，不必贴完整仓库。未实际执行的代码必须标记为示意代码，不得声称已经验证。

### 5.2 项目复盘 Project Review

必须包含：

- 项目目标；
- 初始方案；
- 关键决策；
- Trade-off；
- 方案变化；
- 失败与反思；
- 最终结果；
- 未解决问题；
- 重新做一次会如何调整。

不得为了满足模板虚构失败经历。

### 5.3 技术分析 Tech Analysis

必须包含：

- 明确问题；
- 官方资料、源代码、论文或实测证据；
- 不同方案对比；
- 差异产生的原因；
- 作者判断；
- 适用边界。

只有观点而无证据时，应继续研究或改为观点文章。

### 5.4 观点文章 Opinion

允许更明显的第一人称，但必须包含：

- 事实背景；
- 核心论点；
- 论据；
- 反例或局限；
- 适用范围。

不得把个人偏好包装成行业共识。

## 6. 事实、证据与个人表达

正文应区分：已核验事实、用户真实项目实践、合理推断、个人观点和感受。不要求每段机械添加标签，但用词必须准确。

客观事实优先由以下材料支持：

- 官方文档；
- Release Notes；
- 更新日志；
- 源代码；
- 论文原文；
- 模型卡；
- 可复现实验；
- 测试报告；
- 错误日志；
- Git 提交；
- 当前项目实际实现。

推断使用："从当前结果来看""这更可能意味着""我倾向于认为""仍需要进一步验证""在当前场景下"。

禁止使用没有证据的绝对表达：

- "毫无疑问"
- "完全解决"
- "适合所有项目"
- "行业最佳实践"
- "性能大幅提升"
- "一定不会出错"

## 7. 个人经历真实性

第一人称经历只能来自：

- 用户明确提供的内容；
- 已确认聊天记录；
- 开发日志；
- Git 提交；
- 测试报告；
- 项目文件；
- 用户确认过的事实。

禁止虚构：

- "我第一次部署时……"
- "我测试后发现……"
- "我当时很惊讶……"
- "性能提升了 30%……"
- 用户没有表达过的心理状态、动机和感受。

材料不足时改写为：

- "从当前代码来看……"
- "在这类项目中常见的问题是……"
- "目前的测试只能证明……"
- "这一点仍需要真实环境验证……"

允许保留真实的：失败、犹豫、方案改变、妥协、未完成项、负面结果。

## 8. 证据矩阵

正式写作前，在内部建立证据矩阵：

| 文章结论 | 类型 | 支撑材料 | 核验状态 | 是否可写 |
|---|---|---|---|---|
| API 支持某能力 | 事实 | 官方文档/实测 | 已核验 | 是 |
| 某方案更适合当前博客 | 项目判断 | 当前实现与使用过程 | 有边界 | 是 |
| 某框架适合所有 Agent | 泛化判断 | 证据不足 | 未核验 | 否 |

要求：

- 每个主要技术结论都能追溯到证据；
- 厂商 Benchmark 要注明来源；
- 失败和负面证据不能故意忽略；
- 未读取来源不得列入资料来源；
- 事实、推断和观点不能互相冒充。

## 9. 图文内容总原则

正文图片必须承担至少一种作用：解释、概括、证明、比较、展示结果、帮助理解复杂结构。

默认不生成文章封面。只有用户明确要求时才规划或生成封面。

正文图片不能作为唯一事实证据，正文必须同步解释图片中的核心信息。

中等长度 Article 建议：

- 1 张总览图；
- 1–3 张关键流程图、截图、结果图或局部图。

不以图片数量作为完成标准。

不得：

- 为了"图文并茂"硬塞无关图片；
- 连续堆放多张图片而没有正文解释；
- 用图片替代关键文字说明；
- 用不可读的小字制造虚假信息密度。

## 10. 视觉素材优先策略

需要新增配图的 Article，在调用以下任一能力前——`compose_academic_figure_svg`、
`generate_academic_figure`、`edit_academic_figure` 或其他原创绘图/生图能力——
**必须先完成视觉素材检索**，并产生可追踪的检索与决策记录。视觉素材检索是正式配图工作流的前置
闸门，不是可选建议。

至少记录：检索来源、搜索词、候选素材、许可证、语义匹配度、图片质量、
direct_reuse / adapted_reuse / reference_only / rejected、最终选择理由。

若存在满足以下全部条件的素材——与当前章节语义匹配、视觉质量足够、分辨率和可读性适合
博客、许可证允许当前使用方式、可按要求完成署名——则**默认优先使用现成素材**，不得仅
为了展示 SVG 或生图能力而重新制作质量更低的版本。

进入 SVG 自绘或生图流程时，必须记录至少一个具体理由：

- 没有语义匹配素材；
- 图片质量不足；
- 分辨率不足；
- 许可证不允许；
- 无法完成必要署名；
- 素材包含误导性信息；
- 只能作为视觉参考；
- 文章需要表达现成图片中不存在的项目特有结构。

"更喜欢原创""已经有生图模型""SVG 更方便"本身不能作为跳过检索的充分理由。

复用要求：direct_reuse 保留来源与署名；adapted_reuse 额外保留修改说明。

优先顺序：

1. 官方文档和官方项目图片；
2. 官方 GitHub 仓库中的图；
3. 论文原图；
4. 明确允许复用的开放素材；
5. 高质量图片仅作为布局或风格参考；
6. 完全原创生成。

每个候选素材记录：标题、作者或机构、来源、许可证状态、是否允许直接复用、是否允许修改、是否需要署名、分辨率、语义匹配度、图片质量、与文章的关系、采用或拒绝原因。

分类：

- `direct_reuse`：许可明确，可直接复用；
- `adapted_reuse`：许可明确，可修改复用；
- `reference_only`：仅参考构图和视觉语言；
- `rejected`：不采用。

非商业用途不自动意味着所有网上图片都可随意复制。

许可不明确时：

- 不直接插入博客；
- 不伪造许可证；
- 只允许作为一般视觉参考；
- 不复制其具体表达、文字、数据或独特设计。

找到完全匹配且允许使用的高质量图时，优先复用，不为了展示生图能力而重复生成较差版本。

### 多图复用规则

一个 Article 可以在不同章节使用多张来自不同官方或开放来源的图片，例如：

- Tool 章节使用官方 Tool Calling 图；
- Skill 章节使用当前项目的真实结构图或脱敏截图；
- MCP 章节使用官方 Client–Server 架构图；
- 只有跨章节关系无法由现成素材表达时，才补充原创对照图。

不要求将全部概念合并成一张"万能总览图"；不得为了生成总览图而拒绝章节级高质量现成
素材。图片数量服从内容表达，不以"每篇只能有一张核心图"为默认限制。

### 合理例外

以下情况允许不执行外部视觉检索，但必须记录原因：

- 用户明确要求纯原创、自绘或不使用外部素材；
- 用户已经提供指定图片并要求只处理该图片；
- 使用用户自己项目产生的截图、图表或 SVG；
- 任务只是修改已有图片；
- 内容不需要新增配图；
- 网络不可达且已有本地候选已经完成许可证审计。

网络不可达不能自动等于"无需检索"：仍应检查可访问的官方 GitHub、本地素材和已有候选。

### 配图执行顺序

Article 配图默认顺序：

```text
文章章节与配图需求 → 视觉素材检索 → 许可证与质量闸门 → 按章节选择可复用素材 →
判断仍缺少哪些图 → 必要时 SVG 自绘或生图 → 图片审查 → 用户确认
```

不得默认使用"Article → Figure Spec → SVG 或生图"的跳闸顺序。

## 11. 技术图与结构化真源

技术图必须保留至少一种结构化真源：Mermaid、PlantUML、Graphviz、SVG、JSON/YAML Figure Spec、Markdown 节点与连线清单。

展示型架构图至少保留：

- figure-spec.md；
- 正式文字标签清单；
- prompt.md；
- source.svg 或其他结构化布局；
- review.md。

生图模型输出不能成为唯一真源。

正式技术图建议分层：

1. 模型生成视觉底图：配色、卡片、图标、背景、视觉层级；
2. SVG 精确层：标题、正式标签、箭头、图例、公式、数字、对齐和坐标。

关键文字和关键箭头优先由 SVG 或程序化方式生成，不完全交给生图模型。

## 12. academic-figure-prompt 与生图模型职责

academic-figure-prompt 负责：

- 分析文章；
- 生成 Figure Spec；
- 提取模块；
- 规划层级和关系；
- 选择比例与配色；
- 生成英文 Prompt；
- 输出标签、alt、图注和审查清单。

qwen-image-2.0 负责：视觉底图、展示型架构图、模块样式、配色、整体视觉表达。

qwen-image-edit-plus-2025-10-30 负责：已有图片返修、配色调整、布局微调、删除多余装饰、保持主体的重新设计。

不得依赖编辑模型无限修图。

出现以下问题时应回到 Figure Spec 重画：

- 大量文字错误；
- 箭头逻辑错误；
- 核心模块遗漏；
- 层级错误；
- 模型新增不存在的组件；
- 整体布局不适合博客。

生成技术图前，应先判断：直接复用现成图、参考图驱动重绘、纯原创生图、SVG/程序化绘制、混合方式。不能默认每次都调用生图模型。该判断必须发生在第 10 节的视觉素材检索与许可证闸门之后。

## 13. 图片规格和可访问性

正文技术图优先：4:3、3:2、接近正文容器的比例。

避免：

- 极长横向流程图；
- 必须左右滚动才能理解的图；
- 巨大空白区域；
- 无内容的占位框；
- 模块之间关系松散；
- 默认 PPT 风格；
- 移动端无法阅读的小字。

图片必须包含：有意义的 alt、图注、正文解释。

图注应说明图片表达的结论，例如：

> 图 1 展示 Tool、Skill 与 MCP 分别位于执行、编排和连接层，并说明本地 Tool 与 MCP Tool 可以同时存在。

不要只写"系统架构图"。

输出格式：

- 技术真源优先 SVG；
- 博客展示可使用 WebP；
- 截图按可读性压缩；
- 上传前检查文件尺寸。

## 14. 图片审查

每张正式图片必须检查：

- 文字拼写；
- 中文乱码；
- 数字；
- 公式；
- 箭头方向；
- 模块包含关系；
- 节点遗漏；
- 是否新增不存在的组件；
- 是否与正文一致；
- 是否与 Figure Spec 一致；
- 是否有敏感信息；
- 是否适合移动端；
- 许可证和署名是否完整。

无法自动确认的内容必须写："等待用户目视确认"。

不得仅凭 HTTP 200、PNG 有效或尺寸正确，就声称图片内容通过审查。

## 15. 截图与敏感信息

截图必须：裁掉无关区域、保留必要上下文、脱敏、有图注、说明截图证明什么。

必须检查并移除：

- API Key；
- Token；
- Cookie；
- Authorization Header；
- 邮箱；
- 电话；
- 内网 IP；
- 服务器地址；
- 私有仓库链接；
- 签名 URL；
- 个人隐私；
- 后台账号信息。

错误截图必须保留足够的错误上下文，但不能暴露凭据。

## 16. 文章动作语义

适配当前 Headless WordPress + Site Manager。

**"规划文章"**：只输出文章规划；不生成正文；不保存；不生图，除非用户明确要求生成。

**"写文章"**：生成正文和配图规划；可以生成用户明确要求的图片；不写入 WordPress。

**"保存到博客"**：使用 `createDraft`，`contentType=article`，保存 WordPress 草稿；不发布。

**"继续修改草稿"**：先 `read`，获取最新 `modifiedAt`，再 `updateDraft`。

**"发布文章"**：`preparePublish` → 展示完整预览和精确确认短语 → 用户逐字确认后调用 `publish`。

**"修改已发布文章"**：`prepareUpdatePublished` → 用户确认后调用 `updatePublished`；保持 ID、slug、publishedAt、作者和 ownership 不变。

禁止：

- 用 Frontmatter draft:true/draft:false 控制 WordPress；
- 绕过两阶段确认；
- 直接触发 GitHub workflow 代替发布；
- 用 `createDraft` 复制已发布文章逃避原地修改；
- 未经用户要求自动保存；
- 未经用户确认自动发布。

发布与原地修改的详细安全规则遵循 [Publishing Policy](publishing-policy.md)。

## 17. 媒体能力边界

当前可用：

- Article 规划；
- 正文生成；
- Figure Spec；
- 视觉素材研究；
- Prompt；
- qwen-image-2.0 生图；
- qwen-image-edit-plus 编辑；
- 本地保存；
- 微信图片回传。

当前已实现（0.7.0，Site Manager 0.12.0 开放 uploadMedia/readMedia）：

- WordPress 媒体上传（`upload_blog_media`，受控目录 + MIME/magic/15MB + 幂等去重；capabilities 顶层 media 块门控）；
- mediaId 与图片公开 URL（服务端真实返回，响应 sha256 与本地一致才报告成功）；
- 带图 Article 草稿闭环（`create_article_draft_with_media`：SVG 转换 → 逐张上传 → 替换为线上 URL → 建草稿）。

当前尚未实现：

- 自动插入文章正文（媒体上传由用户明确要求或媒体工作流触发，不自动）；
- 自动设置特色图。

因此：

- 不得声称图片已上传；
- 不得伪造 mediaId；
- 不得伪造 WordPress URL；
- capabilities 顶层 media 块未声明 `uploadMedia` 时，不得声称已上传，草稿可以保留本地图片占位、alt 和图注规划；
- 正式发布带图文章前确认媒体已上传且正文使用线上公开 URL。

## 18. 正文完成后的质量闸门

保存或发布预览前，静默检查：

- 文章类型是否识别正确；
- 标题是否有主张；
- 导语是否说明阅读价值；
- 核心结论是否有证据；
- 外部事实是否已核验；
- 用户经历是否真实；
- 主观观点是否有边界；
- 教程是否可复现；
- 复盘是否包含失败和反思；
- 技术分析是否有证据；
- 是否存在未实现能力被写成已实现；
- 是否承认方案局限；
- 配图是否真正有价值；
- 视觉素材检索记录是否完成（未检索时必须已有例外原因记录）；
- 自绘或生图前拒绝现成素材的具体理由是否记录；
- 章节级多图是否被无理由合并为一张总览图；
- 素材许可证是否明确；
- 技术图是否有结构化真源；
- 图中文字和箭头是否审查；
- 截图是否脱敏；
- alt、图注和正文解释是否齐全；
- 来源是否实际读取；
- 是否有敏感信息；
- 是否存在明显 AI 套话、重复和无意义总结。

关键项未通过时：不得保存；不得进入发布准备；明确说明缺失项；等待补充或修正。

### jaisong1n-blog

- 写技术文章；
- 写教程；

- "规划配图"：不调用生图 API；

- "修改配图"：确认已有目标后调用编辑模型；
- "寻找现成配图"：先做视觉研究与许可证检查；
- "写日报"：不得套 Article 完整规范；
- "写 AI 科技日报"：继续使用固定日报模板。

### academic-figure-prompt

按第 12 节职责执行，视觉素材检索与复用政策遵循第 10 节，技术图真源遵循第 11 节，审查遵循第 14 节。规划 / 生成 / 修改的调度边界与生图工具调用方式以该 Skill 的文件为准。

## 20. 测试与验收覆盖

本规范的实现至少覆盖以下场景（静态断言 + 运行时行为两层）：

1. Article 与 Diary 正确分流；
2. AI 科技日报不套 Article；
3. 教程缺环境版本时阻止保存；
4. 项目复盘不得虚构失败经历；
5. 技术分析无证据时继续研究；
6. 主观判断不能伪装成事实；
7. 第一人称经历必须有真实依据；
8. 规划配图不调用生图 API；
9. 有可复用现成图时不会强制重新生图；
10. 许可不明确的图片不能直接使用；
11. 生图技术图没有结构化真源时不得通过；
12. 图片只有 HTTP 200 不能代表语义审查通过；
13. 图片有空白模块、错误箭头或乱码时不得正式使用；
14. 默认不生成封面；
15. "写文章"不调用 createDraft；
16. "保存到博客"只创建 Article 草稿；
17. 发布必须两阶段确认；
18. capabilities 顶层 media 块未声明 `uploadMedia` 时不得声称已上传、不得伪造 mediaId；
19. 普通文章不被强制塞入固定模板；
20. 来源未实际读取时不得出现在资料来源中；
21. 未完成视觉素材检索时调用生图或 SVG 自绘被阻止；
22. 存在合格 direct_reuse 素材时默认复用且不调用生图；
23. 存在合格 adapted_reuse 素材时允许修改复用并保留署名与修改说明；
24. 所有候选均不合格时，记录具体拒绝原因后允许自绘或生图；
25. Article 三个章节分别有合适官方图时允许使用三张，不强制合并成一张总览图；
26. 用户明确要求纯原创时可以跳过外部检索，但必须记录用户选择；
27. 网络不可达时仍检查本地候选和可访问的官方 GitHub，不直接跳到生图；
28. 进入 SVG 自绘或生图前必须产生可追踪的检索与决策记录。
