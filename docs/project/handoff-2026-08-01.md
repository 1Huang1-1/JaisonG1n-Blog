## Implemented locally but still requiring acceptance

### Site Manager 0.8.0 reviewed diary publishing

The current feature branch adds a deliberately two-stage diary publication path:

1. An authorized agent requests `preparePublish` with the diary identifier and `expectedModifiedAt`.
2. The server validates the draft and returns a short-lived, single-use confirmation token.
3. The agent explicitly calls `publish` with that token, the same version expectation, and an idempotency key.
4. The server publishes through the normal WordPress status path, records the audit event, and allows the normal deployment automation to run.

The design also requires a WordPress setting plus a per-diary grant before publication is possible. The AI role does not receive the native WordPress diary-publish capability. Tokens are hashed server-side, expire after ten minutes, are single use, and must never be recorded in logs.

Repository documentation and tests describe this work as implemented locally. It remains pending for real WordPress installation, capabilities confirmation, and end-to-end production acceptance. The project state file contains both this 0.8.0 implementation note and an older 0.7.0 basic-information block; this must be reconciled by a dedicated state-summary task before using it as a single version authority.

## Main gaps and improvements needed

### 1. Reconcile source of truth and Git delivery

The project now has meaningful work on the current feature branch that is not on `origin/master`, while the diary sharing/avatar fix is already on master. The next owner should review the branch diff, decide what belongs in a release, run the relevant checks, merge deliberately, and only then rely on the master-triggered deployment workflow.

The untracked `docs/project/development-log/` files and `docs/research/` also need a review. They contain useful history but are not currently committed, so a clone or another machine will not see them until they are intentionally added.

### 2. Production acceptance of controlled publishing

Before exposing agent publication in practice, install the intended Site Manager version and run an explicit production acceptance sequence: read capabilities, confirm the setting and per-diary grant, create/read/update a draft, prepare publication, verify no mutation during preparation, publish with `expectedModifiedAt`, replay the idempotency key, verify exactly one status transition and one expected build request, then verify the public page. This must be conducted without exposing credentials or confirmation tokens.

### 3. Make WordPress synchronization failures observable and recoverable

The successful retry demonstrates that some build failures are transient, but not that the process is fully reliable. Capture the relevant GitHub Actions logs when failures occur, distinguish WordPress connectivity from Astro build failures, retain bounded retries and clear error messages, and verify that a retry cannot create duplicate deployment triggers.

### 4. Prevent content encoding regressions

The malformed Chinese diary draft demonstrated a concrete integration risk. Keep API clients UTF-8-safe end to end, verify title and body after every create/update, and repair or discard malformed drafts before publication. The exact request technique used for the repair should be retained in the relevant task log, not inferred from the UI.

### 5. Complete UI-level acceptance for sharing and albums

The deployed diary share component and avatar asset were verified by HTTP/component presence. A manual browser check should still cover opening the share modal, QR rendering, copy-link feedback, poster download, narrow mobile layouts, and failure states. Album synchronization likewise needs a public-page acceptance check once its deployment state is known.

### 6. Keep agent boundaries intact

Future sessions must use `docs/agents/ai-content-api-usage.md` before blog API calls, use live capabilities as authority, avoid ordinary WordPress endpoints as a bypass, never create an album through the AI API, and never log passwords, tokens, authorization headers, cookies, application passwords, or private data. For content tasks, draft is the default and publishing requires an explicit user instruction plus the server’s actual capability and authorization response.
